# Running a demo call

## One-time setup (already done on this machine)
- `.env` has real credentials for Twilio, Deepgram, ElevenLabs, Groq, NVIDIA NIM, Neon,
  Telegram.
- `ngrok` installed and authenticated (`scripts/start_all.ps1` resolves its path
  automatically even if it's not on `PATH` yet).
- `uv sync` has been run at least once.

## Every time you want to run a demo

1. **Start everything**: double-click `scripts/start_all.bat` (or run it from a terminal).
   This opens two visible PowerShell windows (brain on 8001, pipeline on 8000 — watch these
   for live logs), starts an ngrok tunnel, and automatically updates `.env`'s
   `PUBLIC_BASE_URL` and the Twilio number's Voice webhook to match the fresh tunnel URL
   (free ngrok assigns a new domain some of the time).

2. **Place the call** — two ways:
   - **Dial the Twilio number directly**: `+14632922519`, if your SIM has ISD enabled.
   - **Have Twilio call you instead** (works around India's outbound-ISD restriction):
     double-click `scripts/trigger_test_call.bat`, or run it with a different number:
     `scripts/trigger_test_call.bat -To +91...`. Defaults to `TEST_CALLER_NUMBER` in `.env`
     if you don't pass `-To`. Add `-BaseUrl https://callmate-pipeline.fly.dev` to call
     through the deployed app instead of your local one.

### Pipeline REST API reference

Both endpoints below live on **pipeline**, not brain (`https://callmate-pipeline.fly.dev` /
`http://localhost:8000`). Both check `SERVICE_TOKEN`, but not the same way — see each
endpoint below — since one of them places real, billable Twilio calls and can't be left open.

**From the interactive API docs** (Swagger UI, auto-generated by FastAPI — no extra setup):
open `/docs` on the base URL above.

#### `POST /v1/calls/outbound` — trigger a real call

`scripts/trigger_test_call.ps1` is a thin wrapper around this
(`pipeline/src/callmate_pipeline/telephony/outbound.py`). Call it directly to ring any number.
`service_token` is a plain field in the request body here (not the Authorize lock) so you can
fill in the whole form and hit **Execute** with nothing else to configure first.

| Field | Where | Type | Required | Notes |
|---|---|---|---|---|
| `to` | JSON body | string, E.164 (`+91...`) | yes | the number that gets called |
| `service_token` | JSON body | string | yes | must equal `SERVICE_TOKEN`, else `403` |

Response: `{"call_sid": "CA...", "status": "queued"}` (Twilio's own call SID/status).

```bash
curl -X POST https://callmate-pipeline.fly.dev/v1/calls/outbound \
  -H "Content-Type: application/json" \
  -d '{"to": "+91XXXXXXXXXX", "service_token": "'"$SERVICE_TOKEN"'"}'
# -> {"call_sid": "CA...", "status": "queued"}
```

This is also the mechanism behind the missed-call-callback idea discussed for working around
carrier restrictions: whatever eventually detects a missed call (e.g. the planned Android
companion app, `android/README.md`) would call this same endpoint with the caller's number.

#### `GET /v1/calls/{call_id}/turns` — turn-by-turn transcript

This one still uses the **Authorize** button (top right of `/docs`) and a real bearer header
— paste `SERVICE_TOKEN`'s value, no `Bearer ` prefix (the lock icon adds that).

Every finished turn (one caller utterance + the assistant's full reply) is written as it
happens (`session/call_session.py` → `storage/repositories.py`, `pipeline.turns` table). This
reads it back.

| Field | Where | Type | Required | Notes |
|---|---|---|---|---|
| `Authorization` | header | `Bearer <token>` | yes | must equal `SERVICE_TOKEN` |
| `call_id` | URL path | string | yes | the call to read; `404` if it doesn't exist |

Response: a list of `{turn_id, caller_text, agent_text, started_at}`, oldest turn first.

```bash
curl https://callmate-pipeline.fly.dev/v1/calls/<call_id>/turns \
  -H "Authorization: Bearer $SERVICE_TOKEN"
# -> [{"turn_id": "turn-3", "caller_text": "...", "agent_text": "...", "started_at": "..."}]
```

`call_id` is logged by both PowerShell windows at call start (`state_transition` log lines are
bound to it), and Twilio's Media Streams URL (`/media/{call_id}`) also carries it.

3. **Answer the call.** Since this is a Twilio **trial account**, you'll hear a disclaimer
   asking you to press any key first — that's Twilio itself, before our app is even involved.
   Press any key to continue.

4. **Wait for the greeting to fully finish speaking**, then talk normally. Wait for the reply
   to finish before speaking again — barge-in/interruption handling isn't built yet
   (`docs/HANDOFF.md` §6.1.5 Week 4 scope), so talking over it will get dropped.

5. **Hang up** when done.

6. **Check the result**:
   - Telegram: you should get a message with the priority/summary (if `TELEGRAM_BOT_TOKEN`/
     `TELEGRAM_CHAT_ID` are set, which they are).
   - Or watch the two PowerShell windows from step 1 — every state transition
     (`ringing → greeting → listening → thinking → speaking`) logs live there.
   - Or query the brain API once there's a seeded user: `GET http://localhost:8001/v1/users/demo/calls`
     (priority/intent/summary) and pipeline's `GET /v1/calls/{call_id}/turns` above (the raw
     turn-by-turn transcript).

7. **Stop everything** when you're done: `scripts/stop_all.bat`.

## Known rough edges right now
- No barge-in — don't talk over the assistant.
- Repeat-call priority bumping (demo scenario #7: 3 calls in 10 min raises priority) needs
  `REDIS_URL` set — it's configured locally (`.env`, pointed at Upstash) and live-verified
  working. **Not yet set as a Fly secret for the deployed `brain`** — deploys there will
  still no-op on this until `fly secrets set --config fly.brain.toml REDIS_URL=...` is run.
- `write_post_call_memory` can occasionally fail on a transient DB/network blip; it's
  isolated so it never blocks the actual reply or the final `session.result` from reaching
  you, but the long-term-memory row for that call may be missing.
- First reply after the greeting can take several seconds (STT finalization + reasoning +
  TTS) — that's expected right now, not a hang.
